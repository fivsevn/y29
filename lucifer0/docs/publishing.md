# 执行与发布

本页说明工具命令、工作记录、配图归档和上线核验。创作方法见[写作与改编](writing.md)，所有来源的表情与称呼转换见[本站化](localization.md)，抽取规则见[抽签规则](lottery.md)，每次更新从[总入口](README.md)开始。

## 准备

使用 Node.js 22 或更新版本。首次使用或依赖变化后，先在仓库根目录执行 `npm ci`，安装图片转换依赖。执行环境提供内置运行时时，执行者自动使用其可用路径。在仓库根目录运行：

```sh
node lucifer0/tools/update.js prepare
```

新一轮先触发 GitHub Actions 采集并等待成功，再读取本次日更材料。返回 `awaiting-intake` 时还未创建发帖操作。有命令行授权时，工具直接请求工作流；没有命令行授权或启动权限时，改用已连接 GitHub 的文件提交能力，不要求浏览器登录。按返回的 `nextAction` 执行：

- `publish-intake-request`：执行者使用已连接 GitHub 的文件工具，在 `requestPublication.branch` 创建或更新 `requestPublication.path`，内容和提交标题分别完整采用 `content` 和 `commitMessage`，不要另外改文件、增加提交正文或把本地工作路径写入请求。文件已存在时先取得当前文件 SHA；完全相同的内容已在 `main` 时只等待，不重复提交。该提交自动启动原采集工作流，无需 `workflow_dispatch` 工具或额外的用户启动命令。
- `wait-for-run`：请求已提交、已启动或正在排队，继续等待后重复同一 `prepare`。保留原工作目录和请求编号。
- `inspect-request-with-connector`：运行状态暂时不可读或启动结果不确定，先通过 GitHub 连接工具核对请求文件与已有运行，避免重复启动；恢复读取后继续同一 `prepare`，不把状态未知解释成采集成功。

请求文件只包含版本、请求编号和时间，不含登录凭据。工具对提交触发的运行额外核对运行头提交中的请求文件，再验证成功运行、机器人子提交、材料标记、文件摘要及当前 `main` 的一致性；核验通过后才同步本次材料。原每日定时采集和手动运行入口保留。

运行失败返回 `intake-failed` 和 `retry-prepare`；核对并处理失败原因后，执行者再次运行同一 `prepare`，工具为尚未创建操作的这一轮生成新请求，由连接工具从当前 `main` 提交，避免重复运行旧头提交。超过24小时的未完成准备也会换新请求。新一轮不足配置所需的六份可用案例、文档有未提交改动或同步失败会明确报错；已准备的旧操作沿用保存的案例数量。保留当前准备状态，按实际原因处理后继续；不覆盖本地改动、不用旧材料或虚构案例补数，也不扣减原流程数量。

准备完成后，工具输出 `operation.json` 与 `reading.md` 的绝对路径。前者保存当前更新的抽签、观察和草稿；后者按来源路径汇集完整规则、人物、世界观、研究和近期几轮帖子原文。早期帖子继续保存在发布包，相关作者与目标串材料由 `brief` 按需取得，避免每轮重读全部历史。账号表登记人物所属世界观；他对他人的了解仍按[写作中的知情边界](writing.md)处理。准备结果中的 `researchWindows` 用于本次素材取样，含义见[抽签规则](lottery.md)。默认工作目录位于仓库外的 `~/.local/state/y29/lucifer0/current`。指定其他工作目录时使用：

```sh
node lucifer0/tools/update.js prepare --work /outside/work
```

`caseAdaptation` 给出案例主帖的固定 `postIds`、建议混排顺序 `rootOrder` 和采集回执 `intakeReceipt`；完整案例保存在 `operation.json.plan.caseAdaptation.items`。`budget` 与 `totalBudget` 用于原创一路，案例的采用量沿原素材另计；`effectiveTotalBudget` 给出包含两路的发布容量，合计不超过 `maxBatchPosts`，当前为120条。这个容量不决定案例串必须有多少回复。按给出的帖号取得案例材料，不在公开 `posts` 增加类型或来源字段。

已有操作再次执行同一命令会恢复当前更新，复用已有的采集回执与案例，保留原编号、预算与抽中的人物，同时刷新阅读材料。同一工作目录只保存一份当前操作；受限操作与另起新轮的边界见[恢复与修正](#恢复与修正)，不在原目录重新采集或重抽计划。

用户明确指定原创数量时，在新更新的准备命令加 `--count N`，案例改编发言另计。参数范围与额度关系见[抽签规则](lottery.md)。恢复时沿用原操作保存的数量与结果。

## 填写当前更新

在 `operation.json` 中填写 `research`、`posts`、适用的 `reviews`、[配图与整轮审读](#生成并归档配图)及[研究补充结果](#研究补充)。其余自动字段由工具管理。工具汇集材料后，执行者实际读完 `reading.md`，再开展观察与写作。

`research` 每项记录一个实际读到的公开页面：

| 字段 | 内容 |
| --- | --- |
| `category` | `news` 正式资讯、`trend` 社交话题、`daily` 日常经历 |
| `purpose` | Meme 观察页填 `"meme"`，其他可省略；Meme 可并入本轮 `trend` 观察，不另设每轮必采任务，见[研究-Meme](../environment/research-meme.md#近期-meme-的观察与取用) |
| `kind` | `feed` 资讯、榜单或单篇材料；`thread` 带回复的讨论 |
| `url` | 原页 HTTPS 链接 |
| `visitedAt` | 实际访问时间，带时区的 ISO 时间 |
| `publishedAt` | 原始发布时间；无法确认时填 `null` |
| `summary` | 实际读到的范围、值得参考的情境或交流；采用时补对应帖子 ID 和改编方向 |

观察覆盖三个类别、至少三个不同页面和两个来源域名，其中有一段实际读到回复的讨论。访问发生在本次更新前 48 小时内，至少一项材料发表于最近七天。旧材料保留原日期，当前话题的热度按本次可读内容记录。

采用当前素材或精选案例时，按[素材取用](../environment/sources-daily-opinions.md#论坛怎样读取)记录，不为补足页面字段恢复原身份或平台，也不单独算作一项新鲜网页观察。

`posts` 使用以下结构；编号由本次更新编号加序号形成，署名在同一账号的后续回复中保持一致：

```json
{
  "id": "update-example-01",
  "author": "guest-example",
  "guest": { "name": "随手取的网名" },
  "createdAt": "2026-11-09T00:00:00+08:00",
  "replyTo": null,
  "text": "这里填写审读完成的发言。",
  "likes": 2,
  "canon": "derivative",
  "media": []
}
```

随机路人的 `author` 使用唯一的 `guest-` 编号，`guest.name` 保存公开网名。署名随帖子归档，网页自动汇集该账号的发言。库内人物使用原 `author` 编号，并省略 `guest` 字段。

`text` 保存实际文字；本站颜文字直接采用[清单](../assets/emotes/kaomoji.json)中的完整 `text`，作为正文保存，不登记为图片。纯图发言填空字符串，并在 `media` 登记实际图片。抓取及其他来源的表达先按[本站化](localization.md)转换，再写入公开字段。

采用讨论审读的操作带有私有 `reviews` 数组，每条实际发言对应一项审读结果：

```json
{ "postId": "update-example-01", "negative": true, "reason": "指责舍友擅自借走设备，要求对方归还。" }
```

`postId` 对应当前 `posts` 中的一条实际发言，`negative` 是终稿态度的布尔判断，`reason` 简短注明实际语气，例如“嫌弃画面难看”“跟着嘲笑”；普通内容同样登记 `negative: false` 并写清依据。修改正文后同步复核。记录只保存在操作文件，不进入公开帖子，也不要求逐条证明动机。涉及事实、知情或具体改写时可填 `reviews.context`；其结构、摘要取得方法及旧操作要求统一见[保存与恢复](lottery.md#保存与恢复)。

整轮负面底线与原创负面机会分别按[负面与回复提示](lottery.md#负面与回复提示)核对，不把底线分摊到每个人或每串。原创回复沿本轮抽中的数量空间，案例回复沿采用的源互动；两路共同核对实际父关系、时间和终稿分类。

`likes` 保存本条基础赞数，取值依据与建议数值的处理见[研究-评论与点赞](../environment/research-comments.md#点赞怎样形成差异)。

主帖的 `replyTo` 为 `null`；回复填写真正父帖的 ID。时间使用带时区的 ISO 格式，按本人时区排定，页面统一以上海时区显示；回复不早于父帖，发言不超过实际当前时刻。新草稿由 `brief` 安排，启用人物时段的操作还核对保存窗口与本人先前发言，处理方式见[逐条写作](#逐条写作)。示例时间与正文在使用时替换为本次实际内容。

删除根帖时，移除整个根串发布包；删除回复时，移除其正文及下级回复，并清理这些发言独用的普通配图。随后重新生成信息流，核对剩余帖子及图片引用。

## 研究补充

准备结果中的 `researchMaintenance.selectedPaths` 给出本次研究对象，抽取方式见[抽签规则](lottery.md#研究补充)。读取选中文档和已有参考，再进入原始来源阅读材料。

围绕本专题尚未解释清楚的问题，连续读原帖及可见回复，再沿实际发生的来回追看后续。一起保留普通、低互动、重复和中断的交流；定向挑选的争执或纠错串用于理解机制，比例判断另需记录采样入口、排序、时间窗口与统计口径。搜索摘要和转述只作发现线索，有效案例以实际读到的原文为依据。

新增前先核对已有案例：同一原串的深化阅读补回原条目，写清这次新增的读取范围与访问日期；有独立价值的新样本沿原编号追加。记录原始日期、实际读到的楼层或分支、影响理解的先后关系，以及未展开、缺失或只见链接的部分。方法上的新发现修订本专题对应章节，已有概括相同的地方合并；过时资料核实后修正。

冲突的触发与转向归[研究-负面与争议](../environment/research-negative.md)，回复怎样参与和接续归[研究-评论与点赞](../environment/research-comments.md)，表达形式与疏漏归[研究-说话方式](../users/research-speech.md)。同一来源在主要专题登记一次，其他专题用链接引用适用处。现有文档能容纳的研究继续在原处深化；确需新增文档时，先向用户说明名称、职责及与现有文档的边界。

当前素材与用户挑选的长期案例沿[素材-每日舆论](../environment/sources-daily-opinions.md)取用，专题只补分析并引用材料日期与标题，不复制整串。自动刷新与本轮研究补充各记实际完成的工作。

完成检查后，将结果填入 `operation.json.researchMaintenance`，每份选中文档对应一项：

| 字段 | 内容 |
| --- | --- |
| `path` | 抽中的研究文档路径 |
| `status` | 实际补充或修正填 `updated`，检查后沿用现有内容填 `checked` |
| `summary` | 本次新增、修正的要点，或检查后沿用原内容的依据 |
| `sources` | 实际读取的来源数组；每项填写 `url`、`visitedAt`、`summary`，分别记录原页 HTTPS 链接、带时区的访问时间和实际读取范围 |

修改研究原文后，用原工作目录再次执行 `prepare`，读取刷新的材料，再继续写作与审读。研究结果随本次更新核验。

## 逐串抽取回复

为原创根串取得本轮回复空间时，先把实际采用的原创新主帖填入 `posts`，再执行：

```sh
node lucifer0/tools/update.js replies --work /outside/work
```

接续旧串时，用根帖 ID 指定目标；多个旧串可重复 `--thread`：

```sh
node lucifer0/tools/update.js replies --thread existing-root-id --work /outside/work
```

命令为原创根串返回 `rootId` 与 `replyCount`；案例根串在 `caseThreads` 中标记为 `mode: "source"`，按已读源帖的实际互动处理，不抽取原创回复额度。两路实际回复都追加进同一份 `posts`，保留真正父帖与先后关系。原创额度与总量关系见[抽签规则](lottery.md)。

## 逐条写作

为一条原创新发言获取独立写作材料：

```sh
node lucifer0/tools/update.js brief --post 本次操作ID-01 --view writer --work /outside/work
```

`--view writer` 只输出本条 `draft` 与 `writer`，完整规则和整轮比较从 `reading.md`、`suggest` 读取，不逐条重复输出。需要核对策划信息时省略该参数，取得完整 `editor`；时间不可用时仍返回原因，`writer: null` 的发言跳过或后续接续。两种输出使用同一抽签与草稿，不影响结果。

案例主帖使用准备结果中固定的 `caseAdaptation.postIds` 作为 `--post`，读取案例全文。按原素材的篇幅、媒体与实际采用的互动形成草稿，调整身份、公开事实与本站时间线，将源回复对应到真正站内父帖。两路草稿写入同一份 `posts`，`rootOrder` 供最终按时间混排参考。

为原创根串取得一条新回复：

```sh
node lucifer0/tools/update.js brief --post 本次操作ID-02 --thread 根帖ID --view writer --work /outside/work
```

已有明确接话对象时使用 `--reply-to`；案例回复也按源关系使用这个入口，不用 `--thread` 重抽目标：

```sh
node lucifer0/tools/update.js brief --post 本次操作ID-02 --reply-to 父帖ID --view writer --work /outside/work
```

`--thread` 与 `--reply-to` 每次选用一个；已有草稿按 ID 读取。原创身份与目标选择见[负面与回复提示](lottery.md#负面与回复提示)。时间由工具在保存窗口内结合本人、父帖和既往发言安排；常用时段是偏好，不为偶尔在其他时段出现补写理由。需要明确指定时间时，使用 `timingExceptions`，合法边界及旧操作区别统一见[身份、处境与可用时间](lottery.md#身份处境与可用时间)。

新临时身份的名字由 `brief` 的独立随机流先分配，保存到 `operation.guestNames[author]`，并填入 `draft.guest.name`；写作者直接沿用。取名只读取本次种子、身份编号与已占用名字，不读取当前帖子、配图或回复内容。既有身份优先沿用原名，恢复和取消操作也保留已存署名；个别应景名按实际语境判断，不将历史网名批量改成另一套统一格式。

把返回的 `writer` 单独交给本条写作者，策划者保留完整阅读包与整轮材料；将完成的文字、图片和已确定身份填入 `draft`，再保存到 `operation.json.posts`。

`writer.createdAt` 是本条时间，`writer.self.voiceExamples` 是标记为 `practice` 的表达练习，其余本人档案保存正式背景。`writer.localization` 随每条发言提供完整本站化规则、颜文字及 L0 图像清单，原创与案例、主帖与回复都读取，不依赖是否抽中媒体机会。原创写作者结合普通动机与抽中的负面倾向开口，案例按 `writer.caseAdaptation` 和源帖处理；创作判断统一按[写作与改编](writing.md)。涉及媒体机会或案例图片时，单条材料提供配图方法，实际取得的文件仍要打开检查。

策划者仅在本条用得上时，从完整阅读包核对本人已知的背景片段，补入单条 `writer`；不能把另一人的档案当作他自然知道的背景。无档案的发言者只需当前发言用得上的处境，无须另编完整经历。每写完一条，先保存初稿，再执行：

```sh
node lucifer0/tools/update.js checkpoint --stage draft --work /outside/work
```

审读并将实际采用的编辑稿保存到 `operation.json.posts`，同步填写终稿分类；需要处境记录时从 `suggest.contextReviewBasis` 取得对应摘要，再执行：

```sh
node lucifer0/tools/update.js checkpoint --stage edited --work /outside/work
```

`checkpoint` 将当前全部 `posts` 的快照、来源及计划摘要保存在外部工作目录的 `draft-history-操作ID.json`，不进入公开信息流。同阶段同内容重复执行不会增加重复快照，后续修订保留新快照，初稿不随终稿被覆盖。把修改依据写入本轮具体审读说明，保存 `reviews` 审读项后再获取下一条材料。完整 `reading.md` 供策划者核对资料。命令中的 ID 替换为实际当前操作编号，回复目标使用草稿或归档中已有的帖号。

整轮 `suggest` 的 `recentUpdates` 提供最近几轮完整发言与媒体，`currentPosts` 提供本轮草稿，策划者按[审读方法](writing.md#审读)检查重复；需要逐条诊断时也可取得完整 `editor`。单条写作者继续使用独立 `writer`，避免从整批稿件学到同一种口吻。

## 生成并归档配图

构思发言时按[配图](writing.md#配图)形成实际媒体。原创读取组合与类型建议，案例沿源帖的画面与用途取得合适素材；草稿写入 `posts` 后，用当前工作目录执行：

```sh
node lucifer0/tools/update.js suggest --work /outside/work
```

命令返回媒体候选、`imagePools` 与 `emotePools` 实际统计，以及 `mediaFollowThrough` 的候选与采用差异；字段与回查方法见[图片与表情抽取](lottery.md#图片与表情抽取)。原创落实适合话头的发图机会，案例核对源帖实际形态，按[配图](writing.md#配图)形成终稿。公开反应表情从本站清单直接引用，来源中的反应图按[本站化](localization.md)转换；外部普通图片及表情用法的研究沿[研究-Meme](../environment/research-meme.md)取材。打开实际文件审读后把采用结果填回操作；基础赞数按[点赞方法](../environment/research-comments.md#点赞怎样形成差异)审定。

每个 `media` 项显式填写 `kind`：普通图片为 `"image"`，表情包或反应图为 `"emote"`。例如：

```json
[
  { "src": "posts/2026/11/update-example-01/media/scene.webp", "alt": "描述实际画面", "kind": "image" },
  { "src": "assets/emotes/l0/huh.webp", "alt": "L0一手托下巴，斜眼看着旁边的问号。", "kind": "emote", "fit": "contain" }
```

`kind` 按实际用途核对，不能把表情标为普通图片。旧帖未填写时继续兼容显示，修订该帖时补齐。公共表情共用 `assets/emotes/l0/`，[L0清单](../assets/emotes/l0/manifest.json)登记唯一的 WebP 文件；`media.src` 直接引用清单路径，多帖可反复引用同一文件，公共图不随旧帖清理。清单随阅读材料和单条写作输入交给执行者。

采用外部素材时，在对应 `research.summary` 保存资源页、作者、使用依据和处理方式；需要署名的素材在帖文或图片画面中保留署名与来源。

普通随帖图片放在所属根串的 `media/` 中；用于回复的文件也归该回复所在根串。本站反应表情统一引用公共清单，新增特制表情先登记为正式资源，不把未登记的外部反应图混放在随帖目录发布。操作文件登记实际路径及 `alt`，头像与界面素材按各自用途保存。

`ingest` 自动把引用的 PNG、JPG、JPEG、SVG 转换为同名 WebP，保留原尺寸、比例、透明度与 `kind`，同步更新操作文件、帖子 Markdown 和信息流的路径，引用保存成功后删除对应旧文件。已是 WebP 的图片不重复压缩。直接上传并由帖子引用的位图也会在构建时转换，Actions 提交新 WebP、引用变化和旧文件删除。

随帖字图等需使用完整画面时，可在 `media` 项填写 `"fit": "contain"`；它控制缩放方式，媒体类别仍由 `kind` 决定。页面采用以下显示方式：

| 位置与媒体 | 显示与查看方式 |
| --- | --- |
| 主页主帖的普通图片 | 可点击的缩略图，点击查看完整画面。 |
| 主页回复的普通图片 | 可点击的 `[图片]` 提示，点击查看完整画面。 |
| 独立讨论中的普通图片 | 按原比例完整显示，保留查看原图入口，小图不放大。 |
| 各页面的 L0 公共表情 | 靠左、按原比例显示，最长边不超过80像素，小图不放大，不提供原图入口。 |

核对图文时同时查看主页和独立讨论，确认缩略图、`[图片]` 入口、正文和小尺寸表情都能正常使用；具体画面与文字检查沿[配图](writing.md#配图)执行。

素材获取或生成受限时，保留当前操作，记录实际完成状态和具体原因，后续沿原操作接续。所需画面不能取得时，按实际表达重整对应草稿，`media` 只登记已取得、已检查的文件。

采用媒体审读的操作，在私有 `mediaReviews` 中为每张实际普通图填写一项，不给表情填写，也不把这些字段放入公开帖子：

```json
{ "postId": "本轮帖号", "src": "posts/2026/11/根帖号/media/scene.webp", "type": "life-photo", "scene": "晚饭吃到一半，从座位上用手机斜拍碗沿，顶灯偏冷，旁边露出餐巾和衣袖。" }
```

`type` 取 `life-photo`（生活照片）、`photo`（其他照片）、`screenshot` 或 `illustration`；`scene` 写实际画面与取景，按[配图定义](writing.md#配图)分类。工具核对逐张记录与真实引用，分类和场景供整轮画面对照使用，不构成生活照片配额。素材复用如实记录，不以另存同图掩盖重复；分类由执行者看图判断，工具不自动识别照片语义或 AI 痕迹。

完成全部文字、媒体、分类和赞数后，再运行 `suggest`，按[整轮审读](writing.md#审读)对照 `recentUpdates`、`currentPosts`、初稿与实际图片。把返回的 `reviewBasis` 两个摘要原样写入私有 `diversityReview`，并填写 `content`、`images` 两项具体审读说明：前者列出相关帖号、重复的叙述路线及实际修改，也记下保留自然相似、随口或低信息表达的理由；后者记实际画面、取景、与近期配图的差异、整页表情疏密，以及 `mediaFollowThrough` 提示的具体候选取舍。说明按本轮具体内容填写，摘要只证明记录对应这份稿件，不代替内容判断。

```json
"diversityReview": {
  "postsDigest": "复制 suggest 返回的 postsDigest",
  "historyDigest": "复制 suggest 返回的 historyDigest",
  "content": "填写本轮具体审读情况",
  "images": "填写实际终稿的看图结果"
}
```

正文、媒体引用或分类记录变化后重新审读并取得摘要；历史变化时先沿原操作 `prepare` 补读，再重新对照。摘要绑定草稿、分类及近期归档，图片文件本身被替换时也须重新打开终稿看图。PNG 等格式转换由导入器同步迁移分类路径，不需要手工篡改摘要。终稿、分类和审读记录一致后再导入；调整内容沿同一操作继续，不删除记录或重抽计划绕过检查。旧操作沿已保存配置恢复，新操作采用当前规则。

## 导入与上线

常规更新须完成计划中固定的案例主帖，不能把空 `posts` 当作一轮日更完成。若已经准备但素材或执行受限，保留操作并按[恢复与修正](#恢复与修正)接续。仅做资料维护时不启动发帖操作；没有固定案例义务的旧操作可以在资料检查、必要提交与核验后沿原工作目录 `finish`，工具返回 `no-posts`。

有待发布发言且审读完成后，用工具输出的实际路径执行：

```sh
node lucifer0/tools/publish.js ingest /outside/work/operation.json --reviewed --ai
node lucifer0/tools/publish.js validate
node build.js
```

导入器核对原创一路的主帖、回复及整体额度、案例一路的固定私有映射，并对两路统一核对账号权限、资料变化、观察记录、帖子编号、父关系、时间、媒体路径、逐条分类与整轮审读摘要。公开文字与反应媒体还须通过[本站化校验](localization.md#发布与历史修订)；来源专有招呼、外部颜文字、emoji 和未登记的反应图在修正后再发布。源帖实际接话关系与表达作用由执行者对照原文审读，工具不代替这一判断。媒体数量与旧操作差异统一按[抽签规则](lottery.md#保存与恢复)核对；候选未采用的具体取舍在整轮审读中说明。资料在创作期间发生变化时，用原工作目录重新执行 `prepare`，读清变化并重新审读原草稿。

帖子 Markdown 是正文来源：

```text
posts/YYYY/MM/根帖ID/
  index.md
  replies/回复ID.md
  media/配图文件
```

每个主帖作为一个发布包，正文、回复和随帖媒体集中在这个文件夹中；跨月回复也放回原包。帖子 Markdown 和包内 WebP 保存这份发布包的原稿与媒体，公共表情沿清单路径引用，网页信息流由这些原稿生成。

导入完成后，确有影响已有用户事实或关系的变化才回写对应原始资料，普通路人片段沿帖子保留；运行仓库检查并查看手机页面。把帖子、配图、必要的资料回写、生成信息流和导入器更新的 `.github/state/lucifer0-case-usage.json` 一起提交，核对最新 `main` 后正常推送。远端有新内容时先合并、补读并检查。保留既有网页样式。

确认 GitHub 构建与 Pages 发布成功，核实本次各张 WebP 均在线上正常加载，并按[页面显示方式](#生成并归档配图)检查主页与独立讨论的媒体入口；普通图片还需打开原图核对完整画面。完成后使用同一工作目录执行：

```sh
node lucifer0/tools/update.js finish --work /outside/work
```

工具核对本地帖子和线上 `https://y29.fivsevn.com/lucifer0/data/feed.json` 的本次内容，成功后清理操作文件、阅读副本，以及能够核对为本轮的工具生成写作包和采集请求。初稿检查点与私有归档保留，其他工作文件不扫描删除；各类文件的边界见[文件保留与清理](#文件保留与清理)。已替换的原格式图片随转换清除。

完成后用一两句简短文字概括本轮实际发布的内容，按需选择读者容易理解的要点，不设固定清单。本轮有新生成的普通配图时，在汇报中直接展示实际已发布的图片，并简短注明所属话题；使用线上归档图片，不另外制作网页截图或重画示例。后台细节仅在影响结果或需要用户处理时简短说明；未发帖时说明实际情况。

## 管理员公告

管理员按用户明确指令编写和发布公告。使用仓库外的人工批次文件，沿本页的帖子结构填写正文；批次的 `version` 为1，`id` 为本次公告编号，`mode` 为 `daily`，`posts` 为实际公告数组。然后执行：

```sh
node lucifer0/tools/publish.js ingest /outside/work/announcement.json --reviewed
node lucifer0/tools/publish.js validate
node build.js
```

公告审读后与必要资料一起提交上线，核验方式沿本页执行；核验完成后清理本次公告批次文件与临时文件。管理员的自动更新范围设为 `none`，抽签权重为0。全站第一帖 `site-welcome` 保存入站须知和访问权限，`/about` 从它的正文读取 `/guide` 与 `/access` 两个栏目，`log in` 弹窗使用同一份访问权限说明；调整时直接编辑这条原帖。首帖正文以“入站须知”为第一行，接一段介绍，规则按 `01 内容`、`02 内容` 连续编号并各占一行；最后以独立一行“访问权限”起一段说明。

## 恢复与修正

中断后继续使用原工作目录、原帖子 ID 和草稿。确无合法时间或取材条件、需要开始另一轮时，保留当前操作与审计文件，在另一个仓库外工作目录以 `prepare --work` 准备新轮；原轮不标为完成，也不在原目录重抽案例或种子。另起新轮前，原轮须尚未开始导入，或已将未完成导入恢复完毕、按[撤回流程](#撤回未完成导入)撤回；换工作目录不能绕过仓库中的未完成写入。已经存在且内容相同的帖子由工具跳过，缺少的部分继续补齐；同 ID 的不同内容会要求核对。

`.publish-pending.json` 暂存未完成导入，`.publish.lock/` 与 `.publish-staging/` 服务写入过程，工作目录的 `.update.lock/` 协调准备、收尾与撤回，均由工具管理。发布校验和构建要求当前导入已完成，准备及恢复仍可读取此前已完成的内容。

执行器被强制结束并留下锁时，AI 先核对该仓库的发布或准备进程已经退出，再清理相应的遗留锁目录，保留当前操作文件与 pending 记录，沿原命令恢复。

推送或上线尚未完成时，继续完成当前步骤；成功核验后再清理工作记录。旧帖修正直接编辑所属发布包中的原 Markdown 和配图，保留帖号；只改措辞时保留作者、时间与父关系，纠正接话或时间错误时同步核对整串。废弃且无其他引用的随帖图片移除，不另建旧稿、补记或修订副本。涉及人物持续经历与研究结论时，改写对应原小结，不在其他文档重复建立规则。

用户明确要求按现行标准整体修订历史时，先逐条读完选定范围的主帖和回复，再把普通图、表情和纯文字连同整串及滚动页面按[审读](writing.md#审读)调整。实际媒体逐张看图、分类，保留丰富的生活画面和自然的局部重复，不按新概率给旧帖重新抽签或补足比例，也不受一次新增更新的预算限制。未要求迁移的历史仍按原记录保留。取得的图片及审读明细暂存仓库外，实际文件只进入所属发布包；修订完成后重新校验、构建、看图和核对线上，再清理临时材料。

补录历史使用用户明确指定的时间范围，并在导入时加 `--backfill`。当时的世界状况与人物阶段决定可用材料。日常更新沿当前时间线追加。

## 撤回未完成导入

旧稿因账号权限变化或内容调整需要重写时，使用原工作目录执行：

```sh
node lucifer0/tools/update.js cancel --work /outside/work
```

工具按当前操作的未完成写入记录逐一核对，只撤回其中仍与记录吻合、尚未进入 Git 的帖子文件。既有帖子、配图和手工改动继续保留；发现文件冲突时保留现场并报告具体路径。

成功撤回后，原操作编号、抽签与观察继续保留，草稿清空，阅读材料刷新。沿同一操作重写、审读并导入。撤回中途被打断时，可重复执行原命令。已经完成归档的正文按旧帖修正流程处理。

## 文件保留与清理

| 文件 | 生命周期与处理 |
| --- | --- |
| 帖子 Markdown、随帖 WebP、公共表情、人物与研究资料 | 属于正式内容，持续保存；历史修订只移除确认不再引用的废弃随帖图片。 |
| `data/feed.json`、`data/feed-index.json`、`data/feed/` | 由正式帖子生成。构建成功写入新索引后，回收不再引用的哈希命名常规分片；未知文件、目录与符号链接保留。 |
| 当前 `operation.json`、`reading.md` | 供当前更新与恢复使用，完成本地及线上核验后由 `finish` 删除；失败时保留。 |
| 工作目录的 `briefs.json`、`intake-request.json` | 只有工具能核对属于当前操作时，随成功收尾清除；不按文件名猜测归属。 |
| `draft-history-操作ID.json` 与私有操作归档 | 保存实际初稿、编辑过程和重放依据，有意保留；不进入网页与后续日常阅读包。长期积累主要占外部归档空间，不增加页面负载。 |
| 锁、pending、staging | 属于进行中事务，按[恢复与修正](#恢复与修正)处理，不用定期清理任务删除。 |
| 执行者自行生成的中间图、下载、截图、评估包等 | 放仓库外的本次工作目录，正式采用的媒体再进入发布包；完成任务、确认无需恢复后清理自己的已知文件，工具不遍历用户目录。 |

正常更新不需要另设定期清理。正式帖子与研究按其价值积累，派生文件由构建或收尾管理；有意保留的审计资料若需调整保留期限，先确定实际归档范围与恢复需要，再单独处理，不能把它们当作无用临时文件批量删除。

## 离线小样对照

调整创作提示或编辑方法、需要判断表达效果时，先从已发布内容选定12条主帖、12条回复，兼顾反复出现的叙述路线与应保留的自然表达。纯粹改变输出视图、保留同一原文的按需读取或清理派生文件时，核对输入范围与结果一致性即可；抽签权重变化另核对采样分布，不用这份表达小样代替概率检查。数量仅用于一次可复查的小样，不作为日常发布配额。保存样本帖号、对应素材、作者、可见父帖、时间及媒体引用，在相同条件下比较原方法与新方法，避免换素材或重抽身份掩盖差异。

两组各自只使用相应的独立写作输入，保存实际初稿、编辑稿与改动依据，混排后隐去方法标签及署名审读。记录哪些不同人物仍共用同一条叙述路线、哪些初稿在编辑时被补成完整故事，以及短回应、自然重复和人物已知范围是否得到保留。几个字的回话无需能辨认作者，改善也不靠缩短全部帖子、统一去标点或提高俏皮话密度判断。

小样沿已有事实试写，不写入公开帖子、素材采用记录或日常发布额度。保留输入快照与评估结果，先据此确定实际需要修改的环节，再用于后续正常更新。

匿名包和空白评分表可由工具导出：

```sh
node lucifer0/tools/writer-evaluation.js blind --input tests/fixtures/writer-trial-v2-20261113.json --methods baseline,v2 --seed review-20261113 --out /outside/review-v2
node lucifer0/tools/writer-evaluation.js report --key /outside/review-v2/key.json --scores /outside/review-v2/completed-scores.json --out /outside/review-v2/report.json
```

审读者只读 `packet.json` 和 `scores.json`，`key.json` 单独保留；原稿保持原文，仅隐去显式署名和方法标签。分别记录自然程度、人物区别、事实矛盾及跨样本重复路线，无法判断的项目可留空；不合成为一个质量总分。同一执行者写作并评估时标记 `independent: false`，不称为独立盲评。

本轮24例沿用旧固定事实和可见范围，原材料中的“目的”已经过整理，因此它只能帮助比较同一材料的表达，不能证明取材已有更多低级、无序的话头。后续评估取材环节时，还需冻结未经诉求归纳的原始脱敏片段，保留本来就杂乱、重复与不完整的内容；不能用这份旧小样代替取材效果检查。

## 持久保存与工作流重放

GitHub Actions 的准备与发布分别使用 `.github/workflows/lucifer0-prepare.yml`、`.github/workflows/lucifer0-publish.yml`。准备流程只手动启动；发布接收实际 `operation_id`，可指定不可变的 `bundle_id`，不再修改脚本里的运行编号、草稿 blob 或帖数。

两份流程从输入 `archive_repository` 或仓库变量 `LUCIFER0_ARCHIVE_REPOSITORY` 读取私有归档仓库（`owner/repo`），`archive_ref` 默认 `main`，该分支须已存在；`ARCHIVE_TOKEN` 需要此私有仓库 Contents 读写权限。未配置时流程在开始处说明缺项，不将未发表草稿和审读记录上传到公开仓库的临时产物中。命令行更新仍可沿本页原流程执行。

归档保存阅读包、原操作与抽签、实际草稿、已有初稿历史和引用媒体，并记录源提交与各文件校验和；`prepared` 和 `reviewed` 分别保存，后续修订保留先前版本。研究、档案、规则及工具源修改先提交，再沿原工作目录 `prepare` 补读并审定；归档工具拒绝未提交的源改动，仅允许本次已经逐字节纳入归档的媒体和指定工作目录。

在源仓库根目录执行，`L0_WORK` 为原工作目录，`L0_ARCHIVE` 为私有归档仓库的本地目录：

```sh
node .github/scripts/lucifer0-operation-archive.mjs save --root "$PWD/lucifer0" --work "$L0_WORK" --archive "$L0_ARCHIVE" --stage prepared
node .github/scripts/lucifer0-operation-archive.mjs save --root "$PWD/lucifer0" --work "$L0_WORK" --archive "$L0_ARCHIVE" --stage reviewed
```

第二条在实际文字、图片与审读完成后执行；随后在归档仓库提交并推送 `operations/`。本地工具本身不联网、不自动推送；准备工作流会保存并提交 `prepared` 版本。

恢复时先把源仓库切到清单记录的 `sourceRevision`，再执行：

```sh
node .github/scripts/lucifer0-operation-archive.mjs restore --root "$PWD/lucifer0" --work "$L0_WORK" --archive "$L0_ARCHIVE" --operation 实际操作编号 --stage reviewed --bundle 实际摘要
```

省略 `--bundle` 时读取该阶段最新版本；复查旧稿时使用明确摘要。工具验证全部文件与目标碰撞后才写入，迁移绝对工作路径时保持原抽签。旧稿可以离线复查，公开发布仍要求源版本与当前 `main` 一致，照常核对素材、父关系、时效、权限和审读；归档不会延长旧操作的发帖时间窗口。
