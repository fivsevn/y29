# 公开内容发布与恢复

## 源数据与归档

一条讨论串一个文件夹。主帖和每条回复都保存为可直接编辑的 Markdown：

```text
posts/2026/11/讨论串编号/
  index.md                    主帖
  replies/
    回复编号.md                一条回复一个文件
rounds/2026/11/本轮编号.json    本轮新增的帖子编号清单
```

文件夹按主帖的年月归档。后来回复旧串时，仍追加到原来的 `replies/`，不搬动主帖。每篇文档顶部保存稳定 ID、作者、带时区的时间、真实回复对象、点赞、样例标记和配图引用，下面是正文。元数据每行一个字段，文本值保留双引号；正文可直接改写。每条回复都有独立编号，`replyTo` 可以指向主帖或另一条回复。

`rounds/` 只记录版本、轮次 ID、模式和本轮新增的帖子 ID，不另存正文。构建根据清单读取对应 Markdown，检查缺失帖子、重复编号、回复关系和错误的目录归属。只有 Markdown 是正文的来源。现有配图继续保存在 `assets/media/`，由文档中的 `media` 引用；这版不把图片移进串包。

提交给导入器的每轮输入仍是一个独立 JSON 批次，最多 7 条动态/回复。帖子必须指定稳定 `author`；没有随机作者、没有覆盖式 trigger。回复和动态使用同一结构，`replyTo: null` 为动态，其他值为真实父帖 ID。

最小批次结构如下。日期、ID 和正文仅用于说明，执行前替换，示例不属于已发布内容：

```json
{
  "version": 1,
  "id": "sample-round-unique-id",
  "mode": "sample",
  "posts": [
    {
      "id": "sample-post-unique-id",
      "author": "alan",
      "createdAt": "2026-11-07T22:00:00+08:00",
      "replyTo": null,
      "text": "经审核的公开日常正文。",
      "likes": 0,
      "canon": "sample",
      "media": []
    }
  ]
}
```

`mode: sample` 对应每帖 `canon: sample`；未来经授权的日常为 `mode: daily` / `canon: derivative`。不提供 `canon: canon`，衍生发言不会自动成为原作事实。时间必须带时区、不在未来、不得早于现有最新内容；它表示网页上的呈现时间，不是定时发布指令，也不自动确定小说时间线。新批次包含回复时，父帖必须存在且不晚于回复，不允许循环。

图片结构为 `{"src":"assets/media/example.webp","alt":"图片文字描述"}`。仅接受仓库内已审核的素材，不自动访问远程图片或上传箱。每帖最多 4 张，路径与 alt 必须合法，素材缺失会在写入前失败。

## 本地审核、导入、提交

1. 将候选批次放在仓库外。结合最新档案、公开历史与知情边界审读每条正文、配图和基础点赞数。不要在公开 PR 中审阅秘密草稿。
2. 审核完成后执行：

   ```sh
   node lucifer0/tools/publish.js ingest /outside/repository/batch.json --reviewed
   npm test
   npm run build
   ```

3. 导入器验证整批内容，确认账号启用、ID/正文未重复、时间与回复合法，然后将主帖和回复写入各自串包，创建 `rounds/YYYY/MM/<batch-id>.json`，更新 `data/feed.json`。普通构建只重建，不发新帖。`--reviewed` 是操作者已审过公开内容的声明，不代表程序能识别剧透。
4. 检查差异及手机预览，提交归档、必要的账号变化、公开记忆和生成信息流到工作分支。正常推送，不覆盖别人的提交。代码/样例通过 PR 审阅，不自动合并。
5. `main` 合并与既有 Pages 成功之后，重新读取线上 feed，核对新增 ID、作者、正文和回复对象，才标记为上线。工作分支、PR 和绿色单元测试都不等于上线。

将来自动任务调用时另加 `--ai`，导入器同时检查 `publication.json` 的总开关和每个账号的 `aiScope`。当前总开关关闭，此路径会拒绝新内容。当前没有安装自动任务，也没有后台调用模型。

## 重试与并发

- 同一轮一直使用同一个批次 ID；同一批次、相同结构和内容重试是无操作，并可补回中断的 feed 构建。
- 同一个批次 ID 携带不同内容会失败，不能靠修改时间、作者或正文规避恢复。
- 帖子 ID 全站唯一，作者/父帖/规范化正文相同也会拒绝重复。
- 导入使用 `.publish.lock/` 互斥，避免两个进程同时通过校验后写入冲突的历史。若进程被强制终止，先确认没有导入仍在运行，再删除遗留的锁目录并用原批次重试。不要删除 `rounds/.pending/` 的恢复记录。
- 先完整验证，再登记本轮待完成的文件与摘要；各文件完整写入暂存目录后，才以禁止覆盖的方式原子落盘。最后建立本轮清单，整轮内容才成为已归档数据。中途失败时，构建只忽略有恢复记录且内容摘要一致的未完成文件；缺失的已归档文件、未登记的文件或被改过的半成品都会报错，不能悄悄丢弃。
- 同一批次重试会复用内容相同的半成品并补齐剩余文件。发现未完成轮次时，先恢复原轮，不能另起一轮绕过。`.publish-staging/` 只保存临时写入文件，不是内容源；确认没有导入运行后可清理其中遗留的临时文件。恢复完成后再提交串包、轮次清单与生成信息流，不提交暂存文件。
- 归档已完成而后续构建失败时，修复原问题并重试原批次，不生成新 ID。源归档与轮次清单是恢复依据。
- 推送前重新拉取并检查最新分支。锁只作用于同一本地副本；不同设备的并发仍靠普通 Git 冲突处理及 CI 全量校验。

需要修正文案时，直接编辑对应 `index.md` 或 `replies/<id>.md` 的正文，保留轮次清单、帖子 ID、作者、时间和回复关系；说明修订原因，重新构建。点赞修改原文档的 `likes`。不要删除被回复的原帖或发一个“修正版”冒充旧帖。人工编辑归档绕过导入器的新帖权限检查，维护者仍须遵守账号与审核规则。

## 构建与隐私

公开源结构拒绝不认识的字段；网页数据另做字段选择，不输出 AI 管理权限。构建仅复制网页、生成 feed、应用图标和登记/帖子中引用的公开图片，不复制运营文档、发布工具或私有档案。公开仓库本身仍可读，**草稿及秘密绝不能进 Git**。

`.gitignore` 是防误操作的补充，不是私密存储。实际私有目录必须位于仓库之外；不依赖 hidden/draft 标记、前端隐藏、构建排除或忽略文件来保护已提交的秘密。
