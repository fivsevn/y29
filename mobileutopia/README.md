已有独立可玩初版，文件位于 `/mobileutopia/`；全站入口目前仍标记 OFFLINE。开发预览与公开入口是否开放是两件事，修改玩法不需要顺带改变入口状态。

## 运行与检查

在仓库根目录运行：

```bash
npm start
# 浏览器打开 http://127.0.0.1:4173/mobileutopia/
node --test tests/mobileutopia.test.js tests/mobileutopia-controller.test.js
npm run build
```

无需第三方运行依赖；使用原生模块，请通过本地服务器预览，不能直接双击 HTML。构建会包含本目录的页面、样式、模型和控制器。

## 当前体验

一晚有 6 个时段，每时段先回应一件小事，再安排两位不同伙伴各做一件事。安排按队列顺序执行，可以先补给再做饭；撤回不会消耗资源。执行两项安排后结算降温、疲劳并进入下一时段。最后一轮同样结算降温，然后在 20:10 开饭。

目标为每人一份饭、一个干燥位置，开饭热度至少 1。结局按饭量、位置、热度及是否聊天判定，共 5 种；没有隐藏善恶分或好感度。

- 四位可安排成员：你、阿岚、老周、小满；阿诚可受邀在第 4 轮到场，增加吃饭人数和食材，不加入安排列表。
- 两个地点：桥洞、路口，初始食材与位置不同。
- 三种固定天气。seed 目前仅用于选择天气方案，不随机生成事件。
- 阿岚做饭多 1 份，老周整理多 1 个位置，小满找菜多 1 份。连续工作两时段要休息，聊天和未分配工作都会恢复精力。

## 文件职责与修改入口

| 想修改什么 | 入口 | 一起核对 |
| --- | --- | --- |
| 成员、技能介绍、任务说明 | `engine.js / CREW、TASKS` | 技能实际效果在 `work`，说明文字不会自动改变规则 |
| 天气、地点初始资源 | `engine.js / NIGHTS、fresh、weather` | `fresh` 当前以 `% 3` 选天气，新增方案需一起改索引；地点 ID 在存档恢复中校验 |
| 每时段对话与选择 | `engine.js / event、step` | `event` 列出选项，`step` 执行效果；选项 ID 必须对应 |
| 资源消耗、产出、疲劳、降温 | `engine.js / work、reason、cooling、step` | `reason` 使用队列预估校验，`work` 执行同一套规则 |
| 五种结尾及优先级 | `engine.js / ending` | 缺饭优先于位置不足，位置不足优先于冷饭；完整条件下再按聊天区分 |
| 设置页、安排页、消息、档案与导出 | `app.js` | `preview` 不扣资源；界面箭头尚未扣除时段结束降温，预报另行提示 |
| 结构与外观 | `index.html、style.css` | 页脚操作、对话框和无障碍播报也由控制器使用 |

规则由 `engine.js` 负责，控制器只展示状态并提交动作。不要只改任务说明或界面数字；每个任务的准入、资源消耗和预估结果必须一致。

## 状态流与存档

```text
fresh → choice → plan（添加 / 撤回安排）→ resolve
             ↑                            ├─ 下一轮 choice
             └────────────────────────────┘
                                          └─ 第 6 轮：ended
```

`available(state)` 返回合法动作，`reason(state, actor, task)` 返回不可安排原因，`preview(state)` 按顺序计算已排任务的效果，`step(state, action)` 执行合法动作并返回新状态。非法动作返回原状态。

当前局的存储键为 `y29.mobileutopia.session.v1`，最近 12 晚的小记为 `y29.mobileutopia.archive.v1`。只保存 `{version, seed, place, actions}`，读取时通过 `restoreSave` 合法重放，不直接相信外部资源数值。撤回会移除对应的待执行动作，避免反复调整计划将存档挤到恢复上限；旧记录中的合法 `undo` 仍可重放。完整流程每轮只保留一次选择、两项安排、一次执行，共 `6 × 4 = 24` 个动作。当前恢复入口保留最多 250 条原始动作的保护，历史已超限的旧档不会自动恢复。

“同一晚，换一种安排”使用相同 seed 和地点重开；“另一个晚上”返回设置页并清理当前局，已完成小记保留。损坏 JSON 会忽略并重新开始；存储被禁或写入失败仍可继续游玩。

修改天气索引、地点 ID、动作 ID、资源规则或时间结构会影响旧记录重放。应先决定迁移与 `VERSION`；新增时段还要同步检查 `TIMES`、6 轮边界、事件数组、界面说明和结算。

## 深化时的验证

1. 先用固定 seed、地点与动作序列复现，避免直接改资源数值伪造路线。
2. 新任务同时改准入 `reason`、执行 `work`、说明 `TASKS`，验证“先补给再消耗”和撤回。
3. 新事件同时改选项和执行分支，验证资源不足、到场时间及结局细节。
4. 测试刷新恢复待执行队列、反复调整计划、完整结算、重开、存储失败。
5. 运行全套 `npm test`、`npm run build`，再在浏览器检查窄屏安排、对话框、文字导出和长日志。

现有测试覆盖三个天气与两个地点的成功路线、600 晚混合选择与全部五种结局、资源边界、疲劳、撤回、旧档重放及控制器存档行为。控制器测试使用简化文档对象，不代表真实浏览器或视觉验收。
