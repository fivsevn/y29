# 阿岚：残响频率 / ARASHI: SIGNAL LOCK

Y.29 的独立终端叙事游戏。站点入口将本作标记为 ONLINE，页面位于 `/signallock/`。

## 运行与检查

在仓库根目录运行，无需安装第三方运行依赖：

```bash
npm start
# 浏览器打开 http://127.0.0.1:4173/signallock/
node --test tests/engine.test.js tests/controller.test.js
npm run build
```

源码使用原生模块，请通过本地服务器预览。构建生成 `dist/signallock/`，正常页面从共用 `assets/fonts/` 读取字体；另有 `dist/signallock-preview.html`，内嵌脚本、样式、两份字体及字体许可，可单独移动和打开。

仓库已包含自定义域名文件 `CNAME`。正式地址、Pages 发布来源与全站构建流程见[仓库说明](../README.md)，不要通过修改本目录重复配置域名。

## 文件职责与修改入口

| 想修改什么 | 入口 | 一起核对 |
| --- | --- | --- |
| 碎片标题、正文、注释 | `engine.js / RECORDS` | 每条为 `[标题, 正文, 注释]`，内容属于游戏衍生片段 |
| 每轮信道、特殊来源、密钥出现时间 | `engine.js / channels` | 信道顺序受 seed 影响；第 1 轮只开放 A，第 2、5、9 轮远端信道带密钥 |
| 操作条件、追踪、错误、回合流 | `engine.js / available、step、risk` | 非法操作必须返回原状态；保留扫描上限和风险恢复阶段 |
| 结局条件及优先级 | `engine.js / result、ENDINGS` | 按 `result` 从上到下命中；文字顺序对应稳定的结局 ID |
| 按钮、说明、存档、日志演出 | `app.js` | 动作名与 `available` 一致；演出期间禁止重入，重开取消旧演出 |
| 终端结构与外观 | `index.html、style.css` | 字体来自 `../assets/fonts/`，保持共用资源路径 |

不要只在界面上修改显示数字：回合上限 15、碎片目标 12、追踪上限 6、错误上限 3、13 种结局目前分布于模型、界面与说明。调整时先搜索对应规则，再更新测试和文案。

## 状态流与规则

```text
boot → status → greeting → round → review → next
                           ↑                ├─ 下一轮 round
                           └─ event ←───────┤  （第 4、8、12 轮后）
                                            └─ final → ended
round / review → risk → cut（ended）或 force（恢复原阶段）
```

每局最多 15 轮，收集 12 个碎片也可提前结算。每轮最多扫描两条信道；第二次扫描增加追踪，后续操作只针对最后扫描的信道，不能切回。锁定接纳数据；验证增加追踪并修复、隔离或拦截；丢弃跳过本轮。追踪达到 6 时需断开或冒险继续，错误达到 3 时结束。

`fresh(seed)` 建立状态，`channels(seed, round)` 生成本轮信道，`available(state)` 给出合法动作，`step(state, action)` 返回新状态。模型不读取浏览器、网络或存储。保持这一层独立，便于用固定种子重现问题。

## 存档兼容

- 当前局：`y29.arashi.session.v1`，仅保存 `{version, seed, actions}`；`restoreSave` 从开局重放并校验动作，不信任外部计数器。
- 已发现结局：`y29.arashi.archive.v1`，保存结局 ID。调整 `ENDINGS` 时保留既有 ID，避免旧档案对应到其他结局。
- 旧版缺少开场 `reply` 的记录会在恢复时补上该动作。
- 玩家数据仅保存在当前浏览器，存储被禁或写入失败时仍可游玩。游戏不会扫描真实网络。

修改随机算法、信道生成顺序、动作含义或结局优先级，都可能使旧动作记录重放出不同结果。此类变更应同时决定迁移方式与 `VERSION`，并用旧存档验证；只改显示文字无需随意提升版本。

## 回归验证

1. 用固定 seed 记录触发问题的真实动作序列。
2. 将规则改动放在模型，将按钮和演出改动放在控制器。
3. 新增结局时先证明玩家能通过合法动作抵达，再加入 `tests/engine.test.js` 的路线验证。结局总数也在 `app.js` 的档案计数和过滤中使用。
4. 检查刷新续玩、风险阶段续玩、演出中重开和存储不可用。
5. 运行全套 `npm test`、`npm run build`；在浏览器检查字体、日志滚动、按钮和窄屏。单元测试使用简化文档对象，不代表视觉验收。

现有测试覆盖全部 13 种结局的真实操作路线、500 局混合选择、扫描边界、旧档兼容、逐字输出取消与恢复。它们验证当前实现，新增机制仍需增加对应场景。
